# Where Does Product Behavior Live?

**Making Meaning Explicit and Executable**

You are reviewing a pull request that looks small: one condition in a guard, a few lines in a callback. The tests pass. Approving it, however, requires an answer the diff does not contain: what is the product supposed to do in the situation this condition guards?

The condition is only one part of that answer. It reads a flag that a callback sets and a state transition in another class clears. A handler further up decides whether the request reaches this code at all. An orchestration step decides which components see the result, and in which order. A default value elsewhere settles what happens when nothing arrives in time. Each piece is reasonable where it is, inside a class with a clear technical responsibility. Together they define a product decision that has no single place where it can be read, discussed or changed.

None of this requires careless engineering; it follows from a sensible way of organizing code. Classes are often cut along technical responsibilities—handlers, services, state machines, schedulers, adapters—and that organization does its job: it shows where requests arrive, where state is kept and where work is dispatched. What it does not necessarily show is who owns a behavioral decision. The structure tells us which component handles which event, but not which part decides what the product does when those events meet. Such a decision often spans several technical responsibilities, and each class holds only the part that happened to fall within its own.

The decision therefore has to be reconstructed whenever someone needs it: by a reviewer judging whether a change alters behavior or only restructures code, by a developer extending a feature or chasing a defect report that describes an outcome nobody intended, by a tester deciding which cases are worth checking. It does not take a distributed system for this to happen; a single C++ process is enough. Several components, technology stacks and teams amplify the problem without creating it. The engineers responsible for each part see only their fragment of the behavior, while product and testing colleagues need to understand the whole, and reconstruction becomes recurring work: repeated by different people, from different starting points, and not necessarily with the same result.

This raises a question that sounds almost too simple: where does product behavior actually live? And how could its meaning be made explicit, so that it no longer has to be reconstructed?

## Three Good Sources, No Coherent Account

The obvious answer is that we already have places for it. Requirements and documentation describe intended behavior, tests demonstrate it, and implementation code determines it. All three are valuable, and consulting them is exactly the right thing to do. The difficulty is that none of them necessarily presents the decisions behind the behavior as a coherent, current whole.

Documentation is written about the product; it is not executed as part of it. It may leave cases open, describe a rule ambiguously, or describe a rule that was changed two releases ago. Nothing forces it to stay aligned with what the product actually does.

Tests are executed, which makes them more trustworthy, but they are evidence about exercised histories. A test shows that a particular sequence of inputs leads to particular assertions, and the rule behind those assertions has to be inferred. Once branching, state and the order of events come into play, the relevant cases multiply, and reconstructing one rule from many individual assertions becomes hard.

Testing also carries a diagnostic signal of its own. Checking a decision like the one in the opening often means constructing several of the classes involved together, faking a clock and replaying events in a carefully chosen order; once the decision spans components, it can also take simulators and running services. When a rule needs that much around it, the effort is telling us something about the design: the rule cannot be exercised by itself because nothing in the design gives it a separate existence.

Implementation code is the authority on actual behavior, and the decision is certainly in there, though only as the combined effect of the pieces described above. Much of that code looks like plumbing, yet it takes part in the decision. Routing an event, filtering a request or fixing the order in which handlers run can each settle something the product cares about, and recognizing such a choice as a decision is left to whoever reads the code next.

So the information is not missing. Each source contains part of the answer. What is missing is an identifiable home for the product's meaning, and so every engineer who needs that meaning has to assemble it again.

## Giving Decisions an Explicit Home

Earlier posts on this blog addressed a smaller version of this problem. [Making state explicit](mastering-state-in-modern-cpp-making-it-explicit.md) turned hidden state into data that is passed in and returned, and [making effects explicit](effects-in-modern-cpp-making-them-explicit.md) turned hidden side effects into returned descriptions. In both cases, a dependency that previously had to be discovered by reading an implementation became visible at an interface. The dependency did not disappear; it acquired a place where it could be seen.

The same move can be applied one level up, to the decisions that define what a product does. Not every line of code is such a decision. A choice is meaningful when a reasonable alternative would change the product's behavior: whether a request made after its deadline is still accepted, which of two competing updates wins, whether an operation that has been cancelled may still complete.

By contrast, whether such a rule is implemented with a switch or a table normally makes no such difference; choices of that kind are mechanics. They matter for performance and maintainability, but whichever is chosen, the relevant semantics and stated guarantees already determine the behavior. Whether a choice is mechanical therefore depends on what has been settled around it, which is why the routing, filtering and ordering described above can carry decisions.

What if every meaningful decision had an explicit, executable home? A rule would no longer emerge from the way a callback, a guard and a filter interact. It would be written once, as code, in a place that owns it.

Being executable does not by itself make that code authoritative, though. It becomes the **canonical** version of the decision—the statement of the rule that the product is meant to realize, rather than a description kept beside it—once it has been reviewed and accepted as such. Every realization of the product, meaning a concrete way of building and deploying it, then has to conform to that version. Reusing its code is the most direct way; where a technology stack cannot reuse it directly, the realization has to match its behavior. Either way, conformance has to be shown, not assumed. Around that version, a realization's mechanics remain free to vary, as long as they make no meaningful choice of their own.

For an existing product, this means recovering decisions that are already implemented. They have to be found, separated from the mechanics they are entangled with, and reviewed, which sometimes reveals that two components disagree about a rule nobody realized they shared. For a new product, the same decisions can be defined explicitly from the outset, before they have a chance to disperse into infrastructure and coordination code. Identifying the meaningful decisions and giving them canonical, executable homes is the first move of an approach I will refer to as **Executable Semantic Architecture (ESA)**.

Meaning comes in two kinds here. Some decisions belong to the product's domain: they would still make sense if the whole product ran in a single process. Whether a late request is still accepted is such a decision. Others exist because of how the product is realized: how often a lost message is retried, how a timeout is interpreted, which delivery guarantee a connection provides. These platform decisions are just as meaningful—a different retry rule can change what a user experiences—but they may change or disappear when the realization changes. ESA makes room for both. This article concentrates on the domain side, because that is where the next move becomes possible.

## Running the Decisions Together

Giving each decision a home already helps. A localized decision can be found, reviewed and tested on its own. A set of individually tested decisions is still not an account of the product's behavior, though. Behavior arises from decisions acting together: the outcome of one becomes the input of another, and the order in which they apply matters. If that combination is supplied implicitly by production adapters and message handlers, the meaning of the whole is scattered again, only one level higher.

The second move is therefore to compose the **same** canonical artifacts into an independently runnable program for a declared domain scope. ESA calls this program the **Domain Application**. It accepts domain inputs, such as a user request or an elapsed amount of time, and produces observable domain outcomes. It runs in a single process, without the production platform. Even when the product itself is a single process, that means running its decisions without the event loop, timers, I/O and hardware around them; when the product spans components, it also means running them without the network and the other services.

The Domain Application executes the very artifacts that realizations of the product are meant to reuse. That sets it apart from a simulator or reference model maintained alongside production: a separately written model of the rules can disagree with the implementation, leaving two truths to reconcile. Its composition is mechanical in a precise sense: the artifacts and the interactions declared between them already settle what it has to do, so it makes no meaningful decision of its own. It routes the output of one artifact to the input of another, keeps a logical clock and applies the declared sequence. Where order, timing or filtering affect an outcome, they are part of what was declared, not something the composition chooses.

The Domain Application is not the product, either. It leaves out the user interface, transport and persistence, as well as the platform behavior and guarantees a deployed system relies on. Its domain semantics still have to be realized and integrated, together with that platform meaning, before they can serve the product's users. What it provides is the product's domain rules running together, so that they can be exercised and inspected as a whole.

## A Game Designed for Phones, Running in One Process

To make this concrete, consider Orbital Orders, a multiplayer variant of the snake game in my [funkysnakes](https://github.com/mahush/funkysnakes/tree/7b63c9562b7d3ecf5e068a503bb30ca5e1b70d0b) project. Its intended setup spreads across several devices. Players watch a shared arena on a large screen and use their phones to send their snakes toward board positions; each order takes effect only after a deliberately varying delay. In the intended distributed placement, each player's order handling runs on that player's phone, while the authoritative game world lives on a shared component.

Such a topology is full of communication, timing and coordination, which are exactly the places where domain decisions can quietly settle into platform code. Cut along technical responsibilities into a phone app and a backend for the shared arena, this game could well produce the pull request from the opening. Its small condition would be one part of a game rule: whether points collected while an order executes actually count. Entanglement is not inevitable in a system like this, but nothing prevents it either.

That distributed realization has not been built. What exists is the domain. Its decisions were given canonical homes in C++17 from the outset, organized around three owners of meaningful state plus a few stateless rules. **Order** owns what a player intends: it accepts submitted orders and holds each one until it is eligible to act, and it is the part meant to run on each player's phone. **Arena** owns the actual world: it activates orders, moves the snakes, and establishes collections and whether an order reached its destination; it is meant for the shared component. **Game** owns the score and the progress of the game and would most likely stay on the shared side as well. These artifacts are composed into a Domain Application that runs in one process, without networking, actors or phones. A small terminal front end runs the game on top of it, with two players sharing one keyboard.

One test from the project's suite, [`BanksPointsOfOrderThatCompletes`](https://github.com/mahush/funkysnakes/blob/7b63c9562b7d3ecf5e068a503bb30ca5e1b70d0b/tests/test_orbital_game_domain_application.cpp#L105), shows that domain running as a whole. It starts a game, submits a single order that sends a snake to a board position past two food items, and advances game time by 1.6 seconds. Time is just another domain input here. No sockets, threads or timers are involved, and nothing has to be assembled around a faked clock, as checking the scattered version from the opening might require. Within that interval, Order passes the order on once it is eligible, Arena activates it and moves the snake through both food items to its destination, and Game settles the score. Points collected while an order executes only count once that order completes, so the completion banks all 20 of them. The test checks exactly that, and it passes: the order is completed, 20 points are credited, and none remain waiting on completion.

Arena's part is exercised indirectly. The test never inspects the board; it observes the consequences that Order and Game derive from Arena's outcomes. The result is small, deliberately so. It shows that decisions meant for a phone and for a shared component already run together in one process and produce an outcome that can be stated in the game's own terms—an order that completes banks the points it collected—without the topology the game is designed for.

It does not show that a distributed realization would preserve that behavior, and reusing the same artifacts would not settle that by itself. On phones and a shared component, the same inputs can arrive later or in a different order than under the logical clock. Whether that outcome survives then depends on the histories such a realization can produce, how it orders and times them, and which guarantees its platform provides. Establishing that requires building one and comparing the two, which is work for later in this series.

## What Changes When Meaning Is Executable

The Domain Application is an enabling result, not the goal. What matters is what becomes possible once meaningful decisions are explicit and their combination can be executed. None of it is a demonstrated saving yet; the rest of this series sets out to make each possibility concrete.

The most immediate change concerns language. When decisions have identifiable homes, they can be named, and the names refer to something concrete. A product manager, an engineer and a tester can discuss whether points collected during an order should count before the order completes and know that they are talking about the same decision in the same artifact, instead of about three private reconstructions of it. A shared vocabulary does not guarantee agreement, but it gives disagreement a precise object.

Named decisions can also be run. Because the same decisions execute together without production infrastructure, a question about domain behavior can be answered by running a history, where previously it required reading code across several components and stacks. The Domain Application thereby becomes a common reference for examining outcomes. When a realization and the reference disagree, the realization is the first suspect; when the reference itself produces a surprising result, the domain decisions are.

Being able to run them also moves the point in a project's life at which domain behavior can be examined. Domain increments can be explored in the Domain Application before a production topology has been chosen. A new rule can be tried against realistic histories and its observable outcomes discussed while it is still cheap to change. Orbital Orders has already been through this. Playtesting its Domain Application through the terminal front end showed me that the delay curve and the route rule needed to change, and I changed both in their artifacts without waiting for a phone or backend realization; neither exists yet. The platform, user interface and integration work still follows, but it starts from domain behavior that has already been examined.

Explicit decisions also change how a change is reviewed, which brings us back to the pull request from the opening. Once domain decisions have explicit homes, and platform decisions are explicit too, a change can be classified by what it affects. A **domain-semantic** change alters a decision in a domain artifact, and the review question is whether the new behavior is intended. A **platform-semantic** change alters realization meaning such as retry, ordering or timeout interpretation; the question is which guarantee changed and whether the domain behavior still holds under it. A **mechanical** change is intended to preserve the relevant semantics and the guarantees stated for them, and the question is what evidence shows that no meaningful choice crept into it. Each class calls for different expertise and different evidence. Classification is not automatic, and a change mislabeled as mechanical can mislead every check that follows.

Faced with the small condition from the opening, the reviewer can now start from where the change lands. In Orbital Orders, the decision behind that condition has a home: the artifact that decides when points count. A change there can alter the rule itself or only rework how the artifact reaches the same answer, and the review has to establish which. A change to the code that delivers orders in a phone or backend realization, once one exists, may legitimately alter platform behavior, such as how often a lost order is retried; the question then is whether the rule still holds under it. If that code starts deciding by itself when points count, the rule has slipped out of its home, and the review can ask where it belongs.

## Delegating Against a Baseline

Those review questions apply to any change, but they become more pressing when implementation is delegated, whether to another team or, increasingly, to an AI agent. Without an explicit reference, the behavior the result must have has to be described in the task itself—a ticket, a specification, a prompt—and each such description is one more reconstruction of meaning, only as complete as its author's understanding at the time. Accepted semantic artifacts change that starting point. They establish a behavioral baseline that exists independently of any task description, so a task can refer to the baseline and state only what it adds. What it adds depends on whether the work is meant to preserve domain behavior or to change it.

Work meant to preserve domain behavior leaves the domain artifacts settled. A refactoring or a change of mechanics has to leave their meaning untouched. Realizing the domain under a different topology means integrating those same artifacts into the concrete system; re-deriving the rules from a description of them would only reintroduce a second interpretation. What such a task must still specify is the platform behavior and the guarantees the realization needs, which the domain artifacts do not cover and which have to be stated and assessed separately. Work meant to change domain behavior is specified as a difference from the baseline instead, so the unchanged behavior need not be described again. The intended semantic difference is agreed first, the affected artifacts are updated and accepted, and the realizations are then adapted to them.

Either way, delegation can answer three questions explicitly: what is already settled, what the work is authorized to change, and what evidence will be needed to accept the result. The reviewer then checks the outcome against those answers and does not have to infer the intent from a diff. This holds whether the implementer is a colleague or an agent; it matters more when much of the implementation is generated. The artifacts themselves do not show that an implementation conforms to them. That has to come from the evidence named in the third question.

## What It Takes, and Where to Begin

Establishing an executable domain reference takes work, and the work is greatest where the problem is most visible: in an existing codebase whose decisions are already scattered. Someone has to locate those decisions, judge which choices are meaningful, separate them from their mechanics, give them homes and compose them, all while the product keeps working.

AI-assisted analysis and refactoring may help with exactly these steps: finding candidate decisions across components, extracting candidate semantic artifacts, composing them into a local Domain Application and adapting production code to reuse them. That may make the approach practical in more existing systems than it would otherwise be. Whether it saves effort overall is not established, and recovered meaning gains no authority merely by having been extracted. It has to be reviewed against the intended behavior, and generated changes against both that behavior and the platform guarantees they rely on.

An executable reference justifies its cost where a decision would otherwise have to be reconstructed again and again: because it spans components, technology stacks or teams, or because it has to survive a change of realization. Where a rule is already readable in one place and nobody needs it outside that code, a separate artifact adds a boundary without removing any reconstruction. The effort also need not cover a whole product at once; a single troublesome lifecycle can be a better place to start.

Whichever lifecycle you start with, the first step leads back to the opening: writing a rule once requires knowing which place owns it. In that pull request, the flag behind the decision is set by a callback and cleared by a state transition in another class, and neither is evidently the place that defines how it may change. Orbital Orders shows that it does not have to come to this. There, the owner was decided before any code was written and has not changed since: the points collected during an order belong to Game until the order's outcome settles whether they count, and the test above checks exactly that.

In your own code, that place may never have been decided; then it has to be found. Neither the classes in the pull request nor the devices Orbital Orders is designed for reveal it by themselves: classes follow technical responsibilities, and placement follows the topology. Even Orbital's owners have so far only been introduced, not derived: why exactly Order, Arena and Game?
